# Documentation Guide

## 6.1 Documentation Philosophy

Documentation in this project is treated as production code.

**Core principles:**

- Documentation must be accurate or removed
- Docs describe intent, not implementation quirks
- Documentation is versioned
- Docs evolve with code
- No undocumented behavior

## 6.4 Mandatory Documentation Structure

Every documentation file must follow this structure:

```markdown
# Title

## Purpose
Brief description of what this document covers

## Scope
What is included and what is not

## Responsibilities
Who owns this domain/feature

## Dependencies
Related systems, packages, or modules

## Constraints
Limitations and boundaries

## Examples
Practical code examples and use cases
```

### Example Documentation File

```markdown
# Payment Processing Module

## Purpose
This module handles all payment transactions including processing,
refunds, and payment method management.

## Scope
- Payment creation and processing
- Refund handling
- Payment method CRUD operations
- Transaction history

Out of scope:
- Payment gateway integration (handled by Gateway module)
- Invoice generation (handled by Billing module)

## Responsibilities
Owner: Finance Team
Maintainer: Backend Team

## Dependencies
- Gateway Service
- User Service
- Notification Service

## Constraints
- Maximum transaction amount: $50,000
- Minimum transaction amount: $1.00
- Supported currencies: USD, EUR, GBP

## Examples

### Creating a Payment

\`\`\`php
$payment = PaymentService::create([
    'user_uuid' => $user->uuid,
    'amount' => 100.00,
    'currency' => 'USD',
]);
\`\`\`
```

## 6.6 Code-to-Documentation Alignment

### Rules

- Every public API must have documentation
- Every Enum must be documented
- Every breaking change must update docs
- Deprecated behavior must be flagged

### Examples

**Documenting Enums:**

```php
/**
 * User status enumeration
 * 
 * Lifecycle:
 * PENDING -> ACTIVE -> SUSPENDED -> INACTIVE
 * 
 * @see documentation/modules/user/STATUS_LIFECYCLE.md
 */
enum UserStatus: string
{
    /** User account pending verification */
    case PENDING = 'pending';
    
    /** User account is active and operational */
    case ACTIVE = 'active';
    
    /** User account temporarily suspended */
    case SUSPENDED = 'suspended';
    
    /** User account permanently deactivated */
    case INACTIVE = 'inactive';
}
```

## 6.7 Versioning Strategy

Documentation must be versioned alongside code.

### Structure

```
docs/
├── v1/
│   ├── api/
│   ├── architecture/
│   └── setup/
├── v2/
│   ├── api/
│   ├── architecture/
│   └── setup/
└── current -> v2/
```

### Rules

- No retroactive changes
- New versions must be additive or clearly breaking
- Always maintain current version link
- Archive old versions but keep accessible

### Version Change Documentation

```markdown
# Version 2.0 Changes

## Breaking Changes
- User UUID format changed from UUID v4 to ULID
- Payment status enum values changed

## Migration Guide
Step-by-step guide for upgrading from v1 to v2

## Deprecated Features
- `user.legacyId` - Use `user.uuid` instead (removed in v3.0)
```

## 6.8 API Documentation Alignment

Documentation must match:

- ✅ Route signatures
- ✅ Request payloads
- ✅ Response formats
- ✅ UUID usage must be explicit
- ✅ Error codes must be documented

### API Documentation Template

```markdown
# Create User

## Endpoint
`POST /api/v1/users`

## Authentication
Required: Yes (Bearer Token)

## Permissions
Required: `users.create`

## Request

### Headers
\`\`\`
Content-Type: application/json
Authorization: Bearer {token}
\`\`\`

### Body
\`\`\`json
{
  "name": "John Doe",
  "email": "john@example.com",
  "status": "active"
}
\`\`\`

### Validation Rules
- `name`: required, string, max:255
- `email`: required, email, unique:users
- `status`: required, enum(active,inactive)

## Response

### Success (201 Created)
\`\`\`json
{
  "data": {
    "uuid": "9b8c5f2a-8d3e-4f1a-9c7b-2e1d3f4a5b6c",
    "name": "John Doe",
    "email": "john@example.com",
    "status": "active",
    "created_at": "2025-12-27T10:30:00Z"
  }
}
\`\`\`

### Error Responses

#### 422 Validation Error
\`\`\`json
{
  "message": "Validation failed",
  "errors": {
    "email": ["The email has already been taken."]
  }
}
\`\`\`

#### 403 Forbidden
\`\`\`json
{
  "message": "Forbidden",
  "error": "You do not have permission to create users"
}
\`\`\`

## Notes
- The `uuid` is auto-generated and cannot be specified
- Internal `id` is never exposed in API responses
```

## 6.9 Inline Documentation Rules

### PHPDoc Usage

**Required for:**
- Services
- Repositories
- Complex methods
- Public APIs

**Example:**

```php
/**
 * Process a payment transaction
 * 
 * This service handles the complete payment flow including:
 * - Validation of payment data
 * - Gateway communication
 * - Transaction recording
 * - Notification dispatch
 * 
 * @param string $userUuid User's unique identifier
 * @param float $amount Payment amount
 * @param string $currency ISO 4217 currency code
 * @return Payment Processed payment instance
 * 
 * @throws InsufficientFundsException When user balance is too low
 * @throws GatewayException When payment gateway fails
 * @throws InvalidCurrencyException When currency is not supported
 */
public function processPayment(
    string $userUuid, 
    float $amount, 
    string $currency
): Payment {
    // Implementation
}
```

### Forbidden

- ❌ Redundant comments
- ❌ Commenting obvious code

**Bad Example:**

```php
// Get the user
$user = User::find($id);

// Check if user exists
if ($user) {
    // Return the user
    return $user;
}
```

**Good Example:**

```php
// Only active users can perform this action
if ($user->status !== UserStatus::ACTIVE) {
    throw new InactiveUserException();
}
```

## 6.11 Documentation Review Gate

### Rule

- No feature is complete without documentation
- Pull requests without updated docs are rejected

### Documentation Checklist

Before merging any PR, ensure:

- [ ] API documentation updated (if applicable)
- [ ] Module README updated (if applicable)
- [ ] Breaking changes documented
- [ ] Examples provided
- [ ] Diagrams updated (if applicable)
- [ ] Changelog entry added
- [ ] Migration guide provided (for breaking changes)

### PR Template Addition

```markdown
## Documentation

- [ ] API documentation updated
- [ ] Module documentation updated
- [ ] Examples provided
- [ ] Breaking changes documented
- [ ] Diagrams updated

Documentation changes: [Link to docs]
```

## 6.12 Forbidden Documentation Anti-Patterns

- ❌ Outdated docs (worse than no docs)
- ❌ Docs without ownership (assign maintainers)
- ❌ Unversioned docs (always version with code)
- ❌ Inline-only documentation (needs external docs too)
- ❌ Copy-paste docs (each module must be unique)
- ❌ TODO comments instead of proper docs
- ❌ Screenshot-only documentation (must have text)
- ❌ Documenting internal implementation details
