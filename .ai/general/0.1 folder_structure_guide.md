# Folder Structure Guide

## 1.1 Folder Structure Philosophy

The folder structure is built on the following principles:

- Strict folderization by purpose
- Clear ownership of code
- Predictable locations
- Scalability without refactoring
- Zero cross-domain leakage

Each business domain is organized into purpose-based folder hierarchies.

A domain owns everything required to function, including:

- HTTP layer
- Business logic
- Persistence
- Enums
- Assets
- Tests

```
│   ├── Payment/

├── Jobs/
│   ├── Payment/
│   ├── Email/

│   └── ...
├── Models/
│   ├── Payment/
│   ├── User/

│   └── ...
├── Mail/
│   ├── User/
│   ├── Payment/
│   ├── Report/

└── views/
    ├── admin/
    │   ├── partials/
    │   └── [pages].blade.php
    ├── auth/
    ├── api/
    └── layouts/
```

### Key Directories

| Directory | Purpose |
|-----------|---------|
| `Http/Controllers/*` | Controllers organized by domain/purpose |
| `Services/*` | Business logic organized by domain |
| `Jobs/*` | Background jobs organized by purpose |
| `Models/*` | Eloquent models organized by domain |
| `Mail/*` | Mailable classes organized by purpose |
| `views/*` | Views organized by domain with partials |
| `Shared` | Cross-domain reusable code (strictly controlled) |
| `Support` | Low-level helpers, traits, base classes |

> **Rule:** No business logic is allowed outside domain-specific folders.

## 1.4 Folder Responsibilities (Mandatory)

### Controllers

**Purpose:**
- HTTP orchestration only

**Organization:**
- Group by domain/purpose (Admin, Api, Auth, etc.)
- Further subdivide by feature within each domain
- Use versioning for API controllers (V1, V2)

**Allowed:**
- Calling services
- Returning responses
- Using Form Requests

**Forbidden:**
- Validation logic
- Business rules
- Direct DB queries

**Example:**
```
Admin/UserController.php
Api/V1/PaymentController.php
Auth/LoginController.php
```

### Requests

**Purpose:**
- Validation
- Authorization

**Rules:**
- One Request per endpoint
- Uses Enums where applicable
- No inline validation anywhere else

```
Requests/
├── StoreUserRequest.php
├── UpdateUserRequest.php
```

### Services

**Purpose:**
- Business logic
- Use-case orchestration

**Organization:**
- Group by business domain (Payment, User, Notification)
- One service per specific responsibility
- Related services stay in the same folder

**Rules:**
- No HTTP knowledge
- No request validation
- No response formatting

**Example:**
```
Payment/PaymentService.php
Payment/RefundService.php
User/UserService.php
Notification/EmailService.php
```

### Models

**Purpose:**
- Persistence mapping
- Database table representation

**Organization:**
- Group by business domain (Payment, User, Notification)
- One model per database table
- Related models stay in the same folder

**Mandatory Fields:**
- `id` (primary key)
- `uuid` (unique)
- `status`
- Audit columns (`created_at`, `updated_at`, `deleted_at`)

**Rules:**
- No business logic in models (use Services)
- Only relationships, scopes, and accessors/mutators
- Use Enums for status fields

**Example:**
```
Payment/Transaction.php
Payment/Payment.php
User/User.php
User/Profile.php
```

### Enums

**Purpose:**
- All constrained values

**Examples:**
- Status
- Types
- Roles
- Categories

```
Enums/
├── UserStatus.php
├── RoleType.php
```

> **Rule:** No magic strings allowed outside Enums.

### Repositories

**Purpose:**
- Query encapsulation
- Complex data access

**Rules:**
- No business logic
- No HTTP dependencies

### Routes

**Rules:**
- Routes are module-scoped
- UUID-based route binding only

```php
Route::get('/users/{user:uuid}', ...)
```

### Migrations

**Rules:**
- Module owns its migrations
- UUID column is mandatory
- Status column mandatory

### Mails

**Purpose:**
- Email template classes
- Email content and logic

**Organization:**
- Group by purpose/recipient (User, Payment, Report)
- One Mailable class per email type
- Related emails stay in the same folder

**Rules:**
- Use markdown templates when possible
- Keep email logic simple
- Pass data via constructor
- Use queues for non-critical emails

**Example:**
```
User/WelcomeEmail.php
Payment/PaymentReceiptEmail.php
Report/MonthlyReportEmail.php
```

**Corresponding Views:**
```
resources/views/emails/
├── user/
│   ├── welcome.blade.php
│   └── password-reset.blade.php
├── payment/
│   ├── receipt.blade.php
│   └── confirmation.blade.php
└── report/
    └── monthly.blade.php
```

### Jobs

**Purpose:**
- Asynchronous task processing
- Background operations

**Organization:**
- Group by job purpose (Payment, Email, Report, Maintenance)
- Related jobs stay in the same folder
- Clear naming indicates job action

**Rules:**
- Jobs should be idempotent when possible
- Handle failures gracefully
- Use appropriate queue channels

**Example:**
```
Payment/ProcessPaymentJob.php
Email/SendWelcomeEmailJob.php
Report/GenerateMonthlyReportJob.php
```

### Views

**Purpose:**
- Presentation layer
- User interface templates

**Organization:**
- Group by application area (admin, auth, api)
- Partials within their parent folder
- Shared layouts in dedicated folder
- Reusable components in components folder

**Rules:**
- No business logic in views
- Use Blade components for reusability
- Keep partials with their parent views

**Example:**
```
admin/partials/sidebar.blade.php
admin/users/index.blade.php
layouts/admin.blade.php
components/alert.blade.php
```

**Rules:**
- Assets organized by application area
- Common assets in shared folder
- Build process maps assets by domain

## 1.5 Shared Directory (Strictly Controlled)

```
app/Shared/
├── Enums/
├── Traits/
├── DTOs/
```

**Rules:**
- Only truly cross-cutting concerns allowed
- Must be approved before adding new code
- No business logic

## 1.6 Forbidden Anti-Patterns

- ❌ Fat controllers
- ❌ Validation in controllers
- ❌ Business logic in models
- ❌ Business logic in views
- ❌ Flat file structures without folders
- ❌ Mixing unrelated concerns in same folder
- ❌ Global helpers for domain logic
- ❌ Hard-coded statuses
- ❌ Using `id` in routes or APIs

## 1.7 Folder and File Naming Conventions

| Item | Convention | Example |
|------|------------|----------|
| Folder | Singular, StudlyCase | `Payment/`, `User/` |
| Controller | StudlyCase + Controller suffix | `Admin/UserController` |
| Service | StudlyCase + Service suffix | `Payment/PaymentService` |
| Job | StudlyCase + Job suffix | `Email/SendWelcomeEmailJob` |
| Model | Singular, StudlyCase | `Payment/Transaction` |
| Mail | StudlyCase + Email suffix | `User/WelcomeEmail` |
| Request | StudlyCase + Request suffix | `StoreUserRequest` |
| View | kebab-case.blade.php | `admin/users/index.blade.php` |
| View Partial | kebab-case.blade.php | `admin/partials/sidebar.blade.php` |
| Enum | StudlyCase | `UserStatus` |
| Routes | kebab-case URLs | `/admin/users` |

## 1.8 Dependency Rules

**Domain folders MAY NOT depend on each other directly.**

Communication must occur via:
- Services (through dependency injection)
- Events (Laravel event system)
- Interfaces (contracts)
- Jobs (queued tasks)

**Folder Dependencies:**
- Controllers → Services (allowed)
- Controllers → Jobs (allowed via dispatch)
- Services → Models (allowed)
- Services → Repositories (allowed)
- Services → Jobs (allowed via dispatch)
- Services → Mails (allowed via dispatch)
- Services → Other Services (allowed via DI)
- Jobs → Services (allowed)
- Jobs → Models (allowed)
- Jobs → Mails (allowed)
- Mails → Models (allowed for data)
- Views → None (presentation only)

**Example:**
```php
// Admin/UserController.php
public function __construct(
    private UserService $userService,
    private NotificationService $notificationService
) {}

// Jobs can be dispatched from controllers or services
SendWelcomeEmailJob::dispatch($user);
```
